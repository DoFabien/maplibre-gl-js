# Baseline MLT actuelle — MapLibre GL JS 6.3

Cette baseline mesure le commit `5f29885fe226bf712aaa127689a9cc70d0472eec`
avec Node 26.7.0 sur un Intel Core i7-1260P. Les 47 cas s'exécutent dans
des processus isolés, avec 3 warmups et 10 itérations.

```bash
npm run bench:mlt-isolated -- --iterations 10 --warmup 3 \
  --output test/bench/baselines/mlt-v6.3-5f29885fe.json
```

Résultats complets :
[`mlt-v6.3-5f29885fe.json`](./mlt-v6.3-5f29885fe.json).

## Pipeline réel GL JS

| Scan, 4 tuiles                      |   5,676 / 9,140 ms |   0,521 / 0,741 ms |                  0,09 |

| End-to-end avec transfert, 4 tuiles | 25,310 / 33,770 ms | 25,612 / 54,610 ms |                  1,01 |

Le end-to-end MLT transfère 1 600 045 octets par itération contre 2 026 424
pour MVT. Il décode 4 layers et 12 colonnes par itération, sans wrapper,
objet `properties`, `Point` ni fallback sur le chemin de rendu mesuré.

La médiane end-to-end est à parité, mais la p95 MLT reste supérieure à MVT.
Le checker compare donc les ratios MLT/MVT normalisés par rapport à cette
baseline, plutôt que des durées absolues trop sensibles au runner.

## Feature-state, symboles et overzoom

- 100 mises à jour `feature-state` prennent 0,675 / 1,055 ms, retiennent
  13 452 octets de données autonomes et ne déclenchent ni wrapper, géométrie,
  propriété, ni redécodage du raw MLT.
- Les symboles points MLT prennent 31,545 / 55,492 ms contre 31,557 / 87,252
  ms pour MVT et créent encore 480 objets `properties` projetés.
- Les symboles lignes MLT prennent 19,849 / 32,246 ms contre 19,495 / 29,170
  ms pour MVT et créent encore 640 objets `properties` projetés.
- L'overzoom z+1, z+2 et z+4 prend respectivement 27,188, 22,197 et 14,281
  ms en médiane. Les trois cas restent à zéro `Point`, wrapper et réencodage
  MVT ; les buffers enfants mesurent 64 523, 14 235 et 1 766 octets.

Les objets `properties` symboles sont la principale matérialisation de rendu
encore visible dans cette baseline. Ils doivent être remplacés par une vue
réutilisable ou un enregistrement `FeatureTable + index` avant de considérer
le lot symboles terminé.

## Choix du transfert worker/main

| Stratégie                     | Total médiane / p95 | Première query médiane | Transféré |   Retenu |
| ----------------------------- | ------------------: | ---------------------: | --------: | -------: |
| Raw copié + decode lazy       |    2,180 / 4,113 ms |               2,082 ms |  20 796 o | 20 796 o |
| Raw partagé                   |    2,073 / 3,127 ms |               1,988 ms |       0 o | 20 796 o |
| Snapshot query + raw fallback |   3,260 / 10,578 ms |               2,879 ms |  31 178 o | 31 178 o |
| FeatureTable complète         |    3,125 / 4,712 ms |               1,297 ms |  35 149 o | 35 149 o |

Le raw partagé est légèrement meilleur sur ce runner et évite la copie
inter-thread. Il dépend toutefois de `SharedArrayBuffer`, de l'isolation
cross-origin côté navigateur et d'un support absent du sérialiseur actuel.
La FeatureTable complète accélère la première query, mais augmente le coût de
construction/transfert et la mémoire permanente. Le snapshot compact conserve
nécessairement le raw pour les propriétés publiques tardives et perd sur les
deux axes.

La stratégie de production retenue reste donc le raw copié, conservé une seule
fois sur le main thread et décodé de façon ciblée à la première API qui en a
besoin. Le partage contrôlé sera réévalué si ses prérequis deviennent garantis.

## Séquence mémoire complète

Le cas `load → query → feature-state → overzoom → reload` retourne 64 résultats,
transfère 220 832 octets et retient explicitement 96 446 octets de raw/cache.
La heap médiane après GC passe de 74 368 016 octets après load à 74 556 584
après reload, soit +188 568 octets sur une séquence qui conserve la tuile, son
cache overzoom et les buffers du reload. Les `ArrayBuffer` passent de 1 026 684
à 1 075 932 octets. Dix répétitions ne montrent pas de croissance retenue non
bornée dans le processus isolé.

Ce scénario compte un seul décodage main thread, lors de la première query. La
mise à jour de state et le reload n'en déclenchent aucun supplémentaire. Il
compte encore 704 objets `properties` : 64 sorties de query et 640 features du
parse state-dependent. Cette matérialisation reste explicitement à supprimer.

## Budgets automatisés

Le workflow nightly exécute les 47 cas avec Node issu de `.nvmrc`, archive le
rapport et vérifie :

- les ratios de durée MLT/MVT normalisés par rapport à cette baseline ;
- les invariants de matérialisation des parcours de rendu, query, state et
  overzoom ;
- les plafonds d'octets transférés/retenus et de mémoire du lifecycle.

Reproduire le contrôle localement :

```bash
npm run bench:mlt-check -- \
  --report test/bench/baselines/mlt-v6.3-5f29885fe.json
```
